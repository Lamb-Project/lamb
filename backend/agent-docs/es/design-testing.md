# Las pruebas como parte del diseño

Escribe el comportamiento esperado antes de ejecutar la prueba. Incluye una pregunta habitual de aprendizaje, una que requiera fuentes, un seguimiento ambiguo y una petición fuera de alcance o engañosa. Las expectativas deben ser observables: usar el fragmento relevante, pedir una aclaración útil o reconocer la falta de evidencia. No evalúes solo la fluidez.

Una ejecución de bypass o debug inspecciona la entrada construida. No evalúa la respuesta final; una consulta directa a la base de conocimiento es una comprobación diferente. Los casos de prueba guardados permiten repetir comparaciones: conserva sus identificadores, el comportamiento esperado y las ejecuciones reales. Ejecuta respuestas reales y evalúalas respecto a la expectativa. Una petición HTTP correcta no es una prueba superada.

Al proponer un cambio, conserva el caso de prueba, vuelve a ejecutarlo y compara las evidencias. Incluye una expectativa deliberadamente incumplida para comprobar que la evaluación detecta fallos. Los juicios del modelo son provisionales: el educador revisa los casos dudosos o con consecuencias. No afirmes causas ni mejoras que las observaciones disponibles no demuestren.
